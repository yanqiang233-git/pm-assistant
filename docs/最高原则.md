# 最高原则

> **本文件是"项目经理助手"全项目最高约束文档。**
> 后续任何修改和讨论前，必须先读取本文件中的要求，并严格遵守。
> 开发对话过程中若形成新的长期约束或共识，必须在当轮同步更新本文件。

---

## 原则一：业务零回归

任何架构调整、模块拆分、目录重组或代码清理，都不允许影响已有业务功能和逻辑。每次变更后，必须确认核心业务行为（导入校验、分包配置、拆分引擎、模板管理、预览、导出）与变更前完全一致。业务正确性永远高于架构优雅性。

## 原则二：模块边界清晰

模块之间通过注册表和约定接口交互，不允许模块之间直接耦合。每个模块拥有自己的入口、状态、视图和项目子目录，不侵入其他模块的领地。共享能力（如比例模板、公共 UI 组件）必须放在明确的共享层，不允许散落在某个模块内部被其他模块隐式依赖。

## 原则三：先读原则再行动

在后续任何一轮修改或讨论开始前，必须先完整读取本文件。如果原则内容与当次操作存在冲突，优先遵守原则，必要时先讨论修改原则，取得共识后更新本文件，再继续操作。

## 原则四：共识回写

开发对话过程中产生的新的长期约束、架构决策或治理规则，必须在当轮及时回写到本文件或对应的架构文档中，不允许仅存在于对话记录里。回写时应标注新增条目的生效日期。

## 原则五：每次开发后更新架构说明和需求

每次开发完成后，必须自动从全局出发审视并更新《系统架构说明.md》，确保架构文档始终与代码实际状态保持同步。架构说明不是一次性文档，而是随项目演进持续维护的活文档。每次开发完成后，必须自动从全局出发，仅站在业务角度更新需求.md文档。

## 原则六：清理优先删缓存不删业务资产

工作区清理永远优先删除缓存、构建产物、临时文件和锁文件，绝不删除业务代码、业务配置、用户数据和样例文件。任何清理操作前必须确认目标文件的性质。

## 原则七：最小必要改动

每次变更只做直接必要的修改，不附带未经讨论的"顺手优化"。不为假设中的未来需求预建抽象。复杂度必须与当前需求匹配，不多不少。

## 原则八：UI 设计规范（2026-04-19 生效）

所有界面开发必须遵循以下视觉规范，确保全局风格统一：

### 8.1 整体风格
- **定位：** 现代桌面工作台风格，专业、克制、层次清晰，不是后台管理表单页，也不是数据大屏
- **色调：** 浅灰蓝背景 + 深色文字 + 品牌蓝（#2563eb）作为唯一强调色
- **质感：** 白色/半透明面板 + 柔和阴影 + 较大圆角，营造轻盈浮起感

### 8.2 布局原则
- **禁止简单自上而下线性堆叠**，主要页面必须采用混合布局（如左右分栏、Grid 多区域）
- 首页采用"左栏项目上下文 + 右栏模块工作区"的双栏布局
- 信息按"主次层级"而非"时间顺序"排列，核心操作区域占最大视觉权重

### 8.3 卡片设计
- 功能模块卡片必须足够大，承载标题、描述、状态标签、辅助元信息等多层信息
- 卡片最小宽度不低于 300px，高度不少于 140px
- 卡片 hover 时有明确的边框色变化 + 背景微调 + 阴影提升 + 轻微上移（translateY）
- 卡片 active 时有按压反馈（scale 收缩）
- disabled 卡片降低透明度但不完全灰死，保留可辨识的结构

### 8.4 色彩与变量
- 所有颜色必须通过 CSS 变量引用，禁止硬编码色值
- 组件命名使用 `wb-*` 前缀（工作台层）、模块层使用各自前缀
- 按钮、输入框、弹窗等通用组件复用统一的变量和圆角体系

### 8.5 字体与排版
- 使用系统字体栈，中文优先 PingFang SC / Microsoft YaHei
- 标题层级清晰：页面标题 20-24px，区块标题 14-16px，正文 14px，辅助文字 12-13px
- 开启 -webkit-font-smoothing: antialiased

### 8.6 交互反馈
- 所有可点击元素必须有 hover 和 active 态
- 状态切换使用 transition 过渡（150-200ms），禁止无动画的状态跳变
- 空态必须有引导文案，不能只显示空白
- 弹窗使用半透明遮罩 + 居中浮层 + 柔和阴影

## 原则九：开发模式优先（2026-04-19 生效）

每当有新功能更新，必须先把开发模式调通，确认功能在 `npm run tauri dev` 下正常运行后，再考虑打包。不允许跳过开发模式验证直接打包成桌面包。同时，对代码的任何改动必须考虑将来能否同时打包为 macOS 应用和 Windows 应用，不引入平台特有的硬编码路径或平台限定的依赖。
